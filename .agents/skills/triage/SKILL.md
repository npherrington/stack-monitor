# Triage Inbox

Work through the repo's untriaged GitHub issues. `ready-for-agent` is the gate for unattended runs: `docs/agents/unattended.md` refuses to start work on an issue without it, so this skill is where "is this specified well enough to build without a human?" gets answered.

GitHub has no Triage status. "Nobody has evaluated this yet" has two spellings, and this skill treats them the same:

- An open issue with **no category label** (`bug` or `enhancement`). Anyone can file an issue on a public repo, and it lands with no labels at all.
- The **`needs-triage` label**, for an issue that's already been accepted and should be looked at again, or that someone wants evaluated before it goes anywhere.

Labels and the open or closed state carry everything after evaluation.

Every comment posted to an issue during triage **must** start with this disclaimer:

```
> _This was generated by AI during triage._
```

## Roles

One **category** label per issue, and at most one **state** label:

| Role                                                     | GitHub                                             |
| -------------------------------------------------------- | -------------------------------------------------- |
| category: broken                                         | `bug`                                              |
| category: new or better capability, refactor, chore      | `enhancement`                                      |
| state: not evaluated yet                                 | open with no category label, or `needs-triage`     |
| state: waiting on the reporter                           | `needs-info`; the category stays off if it was off |
| state: fully specified, an unattended agent can build it | `ready-for-agent`                                  |
| state: a person has to build it                          | `ready-for-human`                                  |
| state: will not be actioned                              | `wontfix`, closed as not planned or as a duplicate |

Any other label (`documentation`, `good first issue`, `question`, ...) is not a triage role. Leave it as it is.

An issue **accepted** with a category label and no state label is wanted but not agent-ready. It stays open and no unattended run will pick it up.

`needs-triage` is removed as soon as you act on the issue, whichever outcome you pick, so the label never lingers next to `ready-for-agent`. If state labels conflict, flag it and ask the maintainer before doing anything else. Change labels with `gh issue edit <n> --add-label` / `--remove-label`, which touch only the labels they name.

## Invocation

The maintainer describes what they want in natural language. Examples:

- "Show me what needs triage"
- "Let's look at #123"
- "Move #123 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Three `gh issue list` queries over open issues, oldest first, each with `--json number,title,labels,author,createdAt` and `--limit 100`:

1. **`--search "sort:created-asc -label:bug -label:enhancement -label:needs-info"`**: never evaluated, including everything filed straight on GitHub.
2. **`--label needs-triage --search "sort:created-asc"`**: marked for evaluation. Some of these will also show up in query 1; list each issue once.
3. **`--label needs-info --search "sort:created-asc"`, with a comment newer than your last "Triage Notes" comment**: `gh issue view <n> --json comments` to check; the reporter has replied.

"What's ready for agents" is `--label ready-for-agent --search "no:assignee -linked:pr sort:created-asc"`.

Show counts and a one-line summary per item, with the source (no category / `needs-triage` / both / reply on `needs-info`). Let the maintainer pick.

## Triage a specific issue

1. **Gather context.** `gh issue view <n> --json number,title,body,labels,author,comments,url`, and any images in the body or comments. Parse prior triage notes so you don't re-ask resolved questions. Read `CONTEXT.md`, `PLAN.md` and the `docs/decisions/` records for the area, then explore the code. Run three checks: (a) **redundancy**: search for an existing implementation by domain concept, not just the request's wording, and report where you looked; if found, it's an already-implemented `wontfix` (step 5). (b) **duplicate**: `gh issue list --state all --search "<terms>"` for the same request; if one exists, it's a duplicate (step 5). (c) **prior rejection**: read `.out-of-scope/*.md` (if the directory exists) and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a short summary of the relevant code, including whether it's already implemented, and whether `PLAN.md` already places it (a later step, or an Open decision). Wait for direction.

3. **Verify the claim.** Before any grilling, check the claim holds up. For a bug, reproduce it from the reporter's steps (the `fix-bug` skill's repro step is the way to do this: a failing test, or curl against the running monitor). Report what happened: confirmed (with the code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed repro makes a much stronger brief.

4. **Grill (if needed).** If the request needs fleshing out, run `/grilling` with `/domain-modeling`, a round of questions at a time, sharpening terms and updating `CONTEXT.md`/`docs/decisions/` inline as decisions land. The grill is a conversation with the maintainer in this session, not comments on the issue.

   If the maintainer ends the grill before the questions are settled, post what's established as triage notes and leave the issue as it is, with its `needs-triage` label if it has one.

5. **Apply the outcome.** Accepting means adding the category label. Never assign the issue: the assignee is the In Progress mark, the team's and the unattended run's to set. In every outcome below, `--remove-label needs-triage` in the same `gh issue edit` call.
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)), then add the label and the category. Post the comment first so the issue is never `ready-for-agent` without a brief. If the label write fails, say so and stop; don't remove the brief.
   - `ready-for-human`: same structure as an agent brief, with a line on why it can't be delegated (judgement calls, external access, design decisions, manual testing). Add the label and the category.
   - accept, not ready: the work is wanted but the grill isn't done. Add the category with a comment and no state label.
   - `needs-info`: post triage notes (template below), add the label, and leave the category as it is.
   - `wontfix`: add the label and close, depending on _why_:
     - **Duplicate**: `gh issue close <n> --duplicate-of <original>`.
     - **Already implemented**: `gh issue close <n> --reason "not planned"`; point to where it lives; do **not** write to `.out-of-scope/`.
     - **Rejected (bug)**: `--reason "not planned"`, with a polite explanation.
     - **Rejected (enhancement)**: `--reason "not planned"`; write to `.out-of-scope/` and link it from the comment ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).

## Quick state override

If the maintainer says "move #123 to ready-for-agent", trust them: add the label and a category, and drop `needs-triage`. Confirm what you're about to do (labels, comment), then act. Skip grilling. This is the route for small issues: the maintainer's judgement stands in for the grill. If there's no brief, ask whether they want one written: an unattended agent works from the issue body and comments, so a one-line issue with no brief gets a one-line spec.

## Needs-info template

```markdown
> _This was generated by AI during triage._

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you:**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info". Mention the issue's author (`@<login>`) so they're notified.

## Handoff

An unattended run settles anything the brief leaves open with its own recommended answer, so put the decisions you care about in the brief, not in the chat.

If `gh auth status` fails, say so and ask for the issue's contents; don't triage from a URL.
