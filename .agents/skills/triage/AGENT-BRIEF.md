# Writing Agent Briefs

An agent brief is a structured comment posted on a GitHub issue when it gets `ready-for-agent`. It is the specification an unattended agent works from. The original description and discussion are context; the brief is the contract.

## Principles

### Durability over precision

The issue may sit at `ready-for-agent` for days or weeks and the code will move in the meantime. Write the brief so it survives files being renamed or refactored.

- **Do** describe interfaces, types, and behavioural contracts
- **Do** name the specific types, function signatures, routes, MCP tools or config keys the agent should look for or change
- **Don't** reference file paths or line numbers: they go stale
- **Don't** assume the current implementation structure will remain

### Behavioural, not procedural

Describe **what** the system should do, not **how**. The agent explores the code fresh and makes its own implementation decisions.

- **Good:** "`stack_status` should give each checkout's ahead count alongside its branch"
- **Bad:** "Open the routes file and add a field on line 42"

### Complete acceptance criteria

The agent needs to know when it's done. Every criterion is concrete and independently verifiable.

- **Good:** "A worktree with a dev server running isn't offered for removal"
- **Bad:** "Removal should work correctly"

Say how each criterion gets proved where it isn't obvious: a node:test case against a fixture repo, curl against the running monitor, or "checked on the page". Anything that needs what the agent doesn't have (a second machine, an Apple Developer ID, a real login session for launchd) goes under **Not verifiable by the agent**, so it's disclosed rather than skipped.

### Explicit scope boundaries

State what is out of scope. It stops gold-plating and assumptions about adjacent features. Include the decisions the maintainer made in the grill that the agent would otherwise re-open: whether the MCP server gets it too, whether it adds a config key, whether existing `stack-monitor.json` files still load unchanged.

## Template

```markdown
> _This was generated by AI during triage._

## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen
**Surfaces:** core / server / mcp / page (whichever are touched)

**Current behaviour:**
What happens now. For a bug, the broken behaviour and how it was reproduced.
For an enhancement, the status quo it builds on.

**Desired behaviour:**
What should happen when the work is done. Specific about edge cases and error conditions.

**Key interfaces:**

- `TypeName`: what changes and why
- `GET /api/path` reply: what it returns now vs what it should return
- Config key: any new option, and its default

**Acceptance criteria:**

- [ ] Specific, testable criterion 1
- [ ] Specific, testable criterion 2

**Out of scope:**

- Thing that should NOT be changed
- Adjacent feature that is separate

**Not verifiable by the agent:**

- Anything needing another machine, a signing identity, or a real login session
```

## Example (illustrative)

```markdown
> _This was generated by AI during triage._

## Agent Brief

**Category:** bug
**Summary:** A linked worktree shows as merged when its branch has commits that aren't on mainline

**Surfaces:** core, page

**Current behaviour:**
A worktree whose branch is one commit ahead of a non-default `mainline` shows as merged on the
Checkouts page, so it's offered for removal. Reproduced with a fixture repo whose config sets
`mainline` to `origin/develop`.

**Desired behaviour:**
A branch counts as merged only when every commit on it is on the configured `mainline`. A
branch with no commits of its own still counts as merged.

**Key interfaces:**

- The git state a checkout carries: its merged flag is read against `mainline`, not `origin/main`

**Acceptance criteria:**

- [ ] A branch one commit ahead of the configured `mainline` is not merged
- [ ] A branch with no commits of its own is merged
- [ ] A node:test case against a fixture repo covers both

**Out of scope:**

- Changing what makes a worktree safe to remove
- The page's layout

**Not verifiable by the agent:**

- How the page looks in Safari's Add to Dock window
```

## Bad brief

```markdown
## Agent Brief

**Summary:** Fix the merged bug

The merged thing is broken. Look at the worktrees file and fix it, around line 150.
```

No category, vague description, a file path and line number that will go stale, no acceptance criteria, no scope boundary, no current-vs-desired behaviour.
